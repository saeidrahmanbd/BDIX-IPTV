## 3. Trigger collisions and sequencing defects

1. IPTV maintenance, IPTV discovery, and International discovery all have daily `0 1 * * *` UTC schedules (07:00 Bangladesh time). They can become concurrent production writers at the same time.
2. The watchdog dispatches workflows at multiple checkpoints to recover missed runs, while each target workflow also owns its own schedule guard. There are therefore two scheduling authorities.
3. The maintenance workflow is not limited to IPTV. Its references include International discovery, International playlist repair/reorganization, International validation/protection, and shared logo operations. This crosses the owner-curated/automation-controlled boundary.
4. The EPG workflow is a downstream listener for five workflows, but those events are completion events, not a durable declaration that the upstream writer successfully published a new, validated playlist state.
5. Both logo workflows are production writers. One is IPTV-only; the other writes both playlists. Their scopes are not equivalent.
6. The maintenance workflow can run a correction pass after an audit/gate failure, then repeat the audit and gate. A failed invariant can therefore cause more mutation attempts in the same run rather than stopping at a clean, reviewable proposal.
7. Maintenance dashboard recovery runs after a failed main maintenance path and commits generated reports. This makes a failed run still capable of creating a production commit and triggering additional downstream workflows.

## 4. Confirmed owner-protection regression

Maintenance run #1589 (`43396136539`) failed in the `maintain` job. The log shows that preflight/helper tests passed, but after the mutation stage the protected IPTV playlist verifier rejected channel-number changes for four existing channels: GTC Punjabi, Manoranjan TV, The Movie Club, and Thikana TV. Run #1588 (`43394733145`) failed with the same four protected-number violations.

This confirms that the production safety gate is detecting mutation-order/authority leakage. The V2 fix is to make protected playlist invariants structural: the normalizer must not be able to rewrite protected channel positions or numbers, and the publisher must compare exact pre/post invariants before any commit.

## 5. Target V2 dependency direction

The intended flow is one-way:

`scheduler → run ledger → policy resolver → one scoped engine → candidate artifact → tests/invariants → single publisher → downstream read-only consumers`

- Scheduler never edits playlists.
- Discovery writes only to discovery candidate queues.
- IPTV engine cannot call International mutators.
- International engine cannot call IPTV mutators.
- Logo engine changes only logo metadata/assets and proves non-logo playlist bytes are unchanged.
- EPG engine publishes only after independent candidate validation and last-known-good checks.
- Reporting consumes published immutable snapshots and never writes playlists.
- Xtream checks and deployments are read-only/infra operations, not playlist maintainers.

## 6. Migration safeguards

- Keep every existing workflow enabled on production until V2 has passed branch-only tests and fixture dry-runs.
- Do not create push triggers on the V2 branch that can write production.
- Do not reuse existing production secrets in new branch workflows unless strictly required and explicitly scoped.
- No V2 test may commit, push, or deploy.
- All candidate writes stay under a temporary path or test fixture directory.
- A future PR must include a manifest of exact workflows to disable and their V2 replacements.
- The production cutover must be a separate, reviewable change after the V2 branch is green.
